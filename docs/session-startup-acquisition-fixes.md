# Исправления SDK для запуска исходных модулей сеанса

Изолированная реализация опирается на `305f4f1` (0.9.15). Версия выпуска и
архивирование OpenSpec ожидают отдельного решения; основная ветка не изменяется.

## API транзакций

`DatabaseSession` предоставляет асинхронные, а `BlockingDatabaseSession` —
синхронные методы с теми же именами:

- `begin_read_only_transaction(&mut self) -> Result<(), DbError>`;
- `commit_transaction(&mut self) -> Result<(), DbError>`;
- `rollback_transaction(&mut self) -> Result<(), DbError>`;
- `transaction_active(&mut self) -> Result<bool, DbError>`.

Они работают на уже принадлежащем сеансу соединении. Вложенный запуск и
завершение без явной транзакции возвращают ошибку. Чтения внутри явной
транзакции не создают отдельного клиента и не завершают её. Вне неё остаётся
прежний автоматический режим. Метаданные и конфигурация во время явной
транзакции отклоняются без изменения её состояния.

PostgreSQL проверяет идентичность транзакции, `READ COMMITTED` и `READ ONLY`.
SQL Server проверяет `@@TRANCOUNT`, сохраняет прежние ограничения протокола,
отключение при тайм-ауте и необходимость пользователя только для чтения.
Вложенность BSL не реализована в SDK. Ошибки чтения откатывают работу;
прерванный future делает соединение непригодным для повторного использования.
В неясном состоянии следующий вызов разрывает соединение. `close` и Drop
также разрывают соединение, вызывая откат на сервере. Проверка состояния
закрытого или потерянного соединения возвращает ошибку, никогда `true`.
Если очистка потребовала отмены PostgreSQL driver, `close` сохраняет его
диагностику отмены. Существующая сигнатура `PostgresSession::cancel_query(&self, ...)`
сохранена; фасад очищает явную транзакцию после успешной отмены.

## Функциональные опции

Измеренный Content `{0,N,...}` принимается только с точным количеством
поддержанных оболочек ссылок, корректными ненулевыми GUID, заголовком,
корнем, местом хранения и флагом. Нативные опции с двумя ссылками и обоими
значениями режима, независимые Designer XML/CF и сохранённые байты UNF
находятся в `tests/fixtures/functional-option-content-native/`.
Публичные поля существующих дескрипторов не изменены. Разрешение типизированной
ссылки на константу проверено отдельно. Неизвестные и повреждённые формы не
дают частично приобретённых значений. Нативный контроль подтверждает грамматику
и оба флага; он не подменяет запуск оригинального модуля UNF у потребителя.

## Проверки

Новый metadata-тест воспроизводит две ошибки на исходном `305f4f1` и проходит
с исправлением. Старые ожидания SQL и диагностик не менялись. Собственный
PostgreSQL 18.6 в `/tmp/open-sdbl-transaction-pg` на localhost:55439, роль
`sdbl_control`, проверяет совпадение PID/XID между чтениями, независимость
сеансов, commit/rollback/state, запрет CREATE TABLE, callback/error/timeout,
отмену запроса, брошенный future, close/Drop, потерю соединения и синхронную
обёртку с AsyncContext/SessionClosed. Исходные demo/buh/unf не используются.

Живой SQL Server недоступен: его поведение покрыто прежними unit-тестами и
проверкой сборки, но новая транзакционная ветка на настоящем сервере не измерена.
Ранее игнорируемые live и maintenance-тесты не включались.

Сборка выполняется с `CARGO_PROFILE_DEV_DEBUG=0`, `CARGO_PROFILE_TEST_DEBUG=0`,
`CARGO_INCREMENTAL=0`, `CCACHE_DIR=/tmp/open-sdbl-ccache`, чтобы не исчерпать
квоту `/tmp`. Обычный sandbox запрещает локальные TCP-сокеты, поэтому сетевые
unit-тесты и собственный PG-контроль выполняются с разрешённым localhost.
Это ограничение среды не исправлялось изменением тестовых ожиданий.

Команды проверок: `cargo fmt --all -- --check`,
`cargo clippy --workspace --all-targets --offline -- -D warnings`,
`RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --offline`,
`openspec validate --all --strict`,
`OPEN_SDBL_TRANSACTION_CONTROL_PORT=55439 cargo test --workspace --offline -j 2`.

Финальный единый workspace-прогон завершился с кодом 0; fmt, Clippy,
rustdoc и strict OpenSpec также прошли. После последнего дополнения контроля
`cancel_query` повторный transaction-тест подтвердил все шесть сценариев.
Подробные локальные журналы: `/tmp/open-sdbl-session-workspace-live.log`,
`/tmp/open-sdbl-session-transactions-final.log`,
`/tmp/open-sdbl-session-clippy-final.log`,
`/tmp/open-sdbl-session-rustdoc-final.log`,
`/tmp/open-sdbl-session-openspec-final.log`.
