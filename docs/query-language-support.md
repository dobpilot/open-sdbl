# Язык запросов 1С: статус поддержки в open-sdbl

Сверка выполнена 2026-09-15 по версии 0.3.64. Перечень возможностей языка
запросов взят из раздела «Язык запросов» Синтакс-помощника платформы
8.3.27.2342. Статус — из кода `open-sdbl` (`src/lexer.rs`,
`src/query/core/parser.rs`, `src/query/core/codegen/`) и спецификаций
`openspec/specs/`.

Обозначения: ✅ поддерживается · 🟡 частично (см. примечание) · ❌ не
поддерживается. В графе «Примечание / реакция» — диагностика, которую
выдаёт компилятор (`QueryDiagnosticKind`), если конструкция встречается в
запросе.

Страницы Синтакс-помощника, по которым проверялись конструкции, названы во
вводных абзацах разделов; открыть страницу можно поиском по её названию.

Обзор проекта, примеры запросов и описание API — в [README](../README.md).

Корпус реальных запросов демо-конфигурации и результат компилятора на них
лежит в `tests/fixtures/demo` (описание — в README рядом): 382 запроса, из
них 381 фикстура метаданных способна разрешить, компилируется 377. Это
измерение, а не оценка: каждая строка таблицы ниже проверяется на пробной
базе, а корпус показывает, на что запросы натыкаются чаще всего.

Каждый скомпилированный запрос корпуса выполняется на настоящей базе
PostgreSQL (`EXPLAIN`): сервер принимает их все. Это отдельная проверка от
голденов — те подтверждают, что SQL такой, каким его задумал компилятор, а
выполнение подтверждает, что сервер его принимает.

## 1. Структура запроса

Порядок предложений по странице «Секция ВЫБРАТЬ (Описание запроса)»:
`ВЫБРАТЬ [РАЗРЕШЕННЫЕ] [РАЗЛИЧНЫЕ] [ПЕРВЫЕ n] <поля> [ПОМЕСТИТЬ …] [ИЗ …]
[ИНДЕКСИРОВАТЬ ПО …] [ГДЕ …] [СГРУППИРОВАТЬ ПО …] [ИМЕЮЩИЕ …]
[ДЛЯ ИЗМЕНЕНИЯ …]`, затем `ОБЪЕДИНИТЬ`, `УПОРЯДОЧИТЬ ПО`,
`АВТОУПОРЯДОЧИВАНИЕ`, `ИТОГИ`. Три модификатора после `ВЫБРАТЬ` идут в
любом порядке — замерено на 8.3.27, все шесть перестановок
`РАЗРЕШЕННЫЕ`/`РАЗЛИЧНЫЕ`/`ПЕРВЫЕ n` дают один результат; повторённый
модификатор — диагностика.

| Статус | Конструкция (RU / EN) | Примечание / реакция |
| --- | --- | --- |
| ✅ | `ВЫБРАТЬ` / `SELECT` |  |
| ✅ | `РАЗЛИЧНЫЕ` / `DISTINCT` | оператор оставляет только проецируемые значения, поэтому `УПОРЯДОЧИТЬ ПО` адресует колонки выборки по позиции, как у группировки и объединения; поле, которого нет в выборке, — диагностика (иначе SQL отказывается: строковая колонка проецируется с приведением к тексту, а упорядочивание шло по самой колонке) |
| ✅ | `ПЕРВЫЕ n` / `TOP n` | `TOP (n)` на MSSQL, `LIMIT n` на PostgreSQL; `n` — целое > 0 |
| 🟡 | `РАЗРЕШЕННЫЕ` / `ALLOWED` | только после первого `ВЫБРАТЬ` оператора, действует на его вложенные запросы, `В (…)`, объединение и виртуальные таблицы; операторы пакета независимы; фильтры не читаются из ролей, а запрашиваются у приложения (`Prepared::restriction_request` → `CompileOptions::restrictions`) как условия на SDBL и оборачивают таблицу в производную `(SELECT … FROM t AS "__restricted" WHERE …)`, у виртуальных таблиц добавляются к их условию (только прямые поля); разыменованные таблицы не фильтруются; в консоли — `\restrict`; подробнее — README «Ограничения доступа» |
| ✅ | Псевдонимы `[КАК]` / `[AS]` | для полей и источников; `КАК` необязательно — замерено на 8.3.27, короткая форма принимается у поля, агрегата, `ВЫБОР`, константы и разыменования, у объекта, соединения, вложенного запроса, виртуальной и временной таблицы, и на неё ссылаются `УПОРЯДОЧИТЬ ПО`, `СГРУППИРОВАТЬ ПО` и `ИТОГИ`; слово ровно одно (`Имя Второе` — синтаксическая ошибка), контекстное ключевое слово псевдонимом быть может (`ВЫБРАТЬ 1 Сумма`), а слово, открывающее следующую секцию (`ИТОГИ`, `ИНДЕКСИРОВАТЬ`), — нет |
| ✅ | Полное имя источника как квалификатор (`Справочник.Товары.Наименование`) | работает, только если у источника нет псевдонима — замерено на 8.3.27; с псевдонимом платформа отвечает «Поле не найдено», и компилятор тоже; путь продолжается разыменованием (`Справочник.Товары.Поставщик.Наименование`) |
| ✅ | Разыменование через псевдоним выборки | платформа его не принимает («Поле не найдено "К.Наименование"» для `ВЫБРАТЬ Т.Клиент КАК К, К.Наименование`, замерено на 8.3.27) — здесь оно тоже диагностика |
| 🟡 | `*` | только без других полей, без `JOIN` и при одном источнике в `ИЗ` (несколько через запятую — диагностика, платформа допускает) |
| ✅ | Запрос без `ИЗ` | в 1С `ИЗ` можно опустить при полностью квалифицированных полях; open-sdbl без `ИЗ` компилирует только выражения без источника (`ВЫБРАТЬ 1`), в том числе с `ГДЕ`: условие превращается в `WHERE` без `FROM`, как отвечает платформа |
| 🟡 | Вложенные таблицы в выборке `Состав`, `Состав.(Поле, …)`, `Состав.*` | компилируются во второй оператор, связанный с главным по ссылке владельца: `CompiledQuery.nested` несёт его SQL, колонки и структурную связь (индексы колонок-ключей с обеих сторон), а главный оператор получает служебную колонку ключа (`service_columns`); платформа делает то же самое — замерено на 8.3.27: она кладёт ключи во временную таблицу `pg_temp.ttN` и читает секцию соединением с ней; `Состав` и `Состав.*` дают ссылку, номер строки и реквизиты, `Состав.(…)` — ровно перечисленные колонки (псевдонимы внутри списка принимаются и отбрасываются); вместе с `ИТОГИ`, в объединении и во вложенном запросе — диагностика; `ПУСТАЯТАБЛИЦА.(…)` / `EMPTYTABLE` не поддержана |
| ✅ | `ПОМЕСТИТЬ <ВТ>` / `INTO`, `УНИЧТОЖИТЬ <ВТ>` / `DROP` | базы-копии только на чтение, поэтому таблица эмулируется CTE `vt1`, `vt2`, …: `ПОМЕСТИТЬ` определяет CTE и возвращает строку `Количество`, `УНИЧТОЖИТЬ` SQL не порождает и скрывает имя (можно определить заново); определения хранит `TempTablesManager`, в `WITH` попадают только достижимые; правила определения — как у вложенного запроса (`*`, отложенные представления и `УПОРЯДОЧИТЬ ПО` без `ПЕРВЫЕ` запрещены); неизвестное или дублирующее имя — `TemporaryTable` |
| ✅ | `ДОБАВИТЬ <ВТ>` / `ADD` (добавление строк в существующую ВТ) | новая CTE `SELECT … FROM vtK UNION ALL <оператор>`, имя переключается на неё; структура сверяется строго (число колонок, виды, цели и ширина ссылок), расширения типа нет; метки колонок остаются от первого определения; поле перед `ДОБАВИТЬ` не обязано иметь псевдоним, в отличие от 1С |
| 🟡 | `ИНДЕКСИРОВАТЬ ПО …` / `INDEX BY`, `ИНДЕКСИРОВАТЬ ПО НАБОРАМ ((…),(…))` / `INDEX BY SETS`, модификатор `УНИКАЛЬНО` / `UNIQUE` | разбирается и проверяется (поля обязаны быть в списке выборки, иначе `TemporaryTable`), SQL не порождает: у CTE индексов нет |
| ✅ | `ИЗ КритерийОтбора.<Имя>(<значение>)` / `FilterCriterion` | объединение `UNION ALL` по одному выбору на каждое поле состава критерия; единственное поле `Ссылка` несёт найденный объект как payload `RTRef ‖ RRRef`, поэтому разыменовывается, группируется и соединяется как ссылка производного источника; ссылочное значение сравнивается своим 16-байтовым идентификатором; критерий, состав которого не достаёт ни одного живого поля, — диагностика |
| ✅ | `ИЗ ЖурналДокументов.<Имя>` / `DocumentJournal` | таблица журнала со стандартными полями `Ссылка`, `Тип`, `Дата`, `Номер`, `ПометкаУдаления`, `Проведен` и собственными графами по именам метаданных; `Ссылка` — ссылка зарегистрированного документа: одна колонка, если журнал регистрирует один вид документа, и пара `RTRef ‖ RRRef`, если несколько, поэтому разыменование и соединение работают как у любой ссылки; `Тип` — значение типа этой ссылки |
| 🟡 | `<Источник>.<ТабличнаяЧасть>.<Поле>` в условии | компилируется в коррелированный `EXISTS` по таблице части: строка владельца отвечает один раз, сколько бы её строк ни подошло — замерено на 8.3.27 (документ с двумя подходящими строками пришёл один раз, `КОЛИЧЕСТВО(*)` = 4, а не 5); секция называется через владельца (`Д.Товары.Количество`), потому что голое `<Состав>.<Поле>` — это обращение к своим колонкам у запроса, читающего секцию источником; колонка секции, хранимая парой ссылки, сравнивается по payload `RTRef ‖ RRRef`, другая сторона расширяется так же, как в обычном сравнении составной ссылки; прочие составные колонки секции — диагностика; вне сравнения путь не поддержан |
| ✅ | `ИЗ <Вид>.<Объект>.<ТабличнаяЧасть>` | табличная часть читается как источник у всех видов, которые её имеют: справочники, документы, планы видов характеристик, планы счетов, планы видов расчёта, бизнес-процессы, задачи и планы обмена; у прочих видов — диагностика |
| ✅ | `ИЗ <ВТ> [КАК Псевдоним]` (чтение временной таблицы) | имя без точки читается как временная таблица, в том числе в соединениях, вложенных запросах и `В (…)`; с псевдонимом источник адресуется только им, без псевдонима квалификатором служит имя таблицы (платформа голое имя объекта не принимает вовсе — это наше послабление); колонки приходят с видами из определения; разыменование — как у вложенного источника |
| ❌ | `ИЗ &ВнешнийИсточник` (ВТ из таблицы значений) | внешние источники данных в компиляторе отсутствуют |
| ✅ | `ИЗ` / `FROM`: несколько источников через запятую | каждый элемент списка — источник со своими соединениями; рендерится цепочкой `CROSS JOIN` в порядке записи; условие соединения видит только источники своего элемента, как в 1С (иначе `UnknownField`); разделители у таких источников ставятся как у базового; элемент со своими соединениями заключается в скобки и присоединяется целиком — платформа отвечает `Товары, Смешанные ПОЛНОЕ СОЕДИНЕНИЕ Клиенты` 26 строками, то есть `13 × (0 ⟗ 2)`, а не 2 (замерено); `*` при нескольких источниках — диагностика |
| ✅ | `ИЗ (вложенный запрос) КАК Псевдоним`, в том числе в соединениях | псевдоним обязателен; колонки подзапроса становятся полями источника с их `ColumnKind`; внутри допустимы объединения, группировка, соединения, `ПЕРВЫЕ`, `РАЗЛИЧНЫЕ`, inline-представления, `УПОРЯДОЧИТЬ ПО` только вместе с `ПЕРВЫЕ`; запрещены `*` и отложенные представления; разыменование — только через колонку-ссылку с одной фиксированной целью; коррелированные ссылки на внешние источники — диагностика; глубина вложенности ≤ 16 |
| 🟡 | `[ВНУТРЕННЕЕ] СОЕДИНЕНИЕ`, `ЛЕВОЕ/ПРАВОЕ/ПОЛНОЕ [ВНЕШНЕЕ] СОЕДИНЕНИЕ … ПО` / `[INNER] JOIN`, `LEFT/RIGHT/FULL [OUTER] JOIN … ON` | источник соединения может нести свои соединения до собственного `ПО` (условия закрываются в обратном порядке), такая группа компилируется в равносильную плоскую цепочку, внешнее соединение первым — замерено на платформе; группа, у которой внешнее соединение `ЛЕВОЕ`/`ПРАВОЕ`/`ПОЛНОЕ`, а вложенное не `ЛЕВОЕ`, — диагностика, потому что плоская цепочка отвечает иначе (замерено: 21 строка против 13); отличие: платформа не видит из вложенного условия внешние источники, мы их допускаем; цепочка любого числа соединений в порядке записи; ссылки разной ширины в равенстве приводятся к `RTRef ‖ RRRef` (фиксированная получает номер типа цели, составная конкатенируется, payload остаётся как есть), две составные сравниваются почленно; `ПО` каждого соединения содержит хотя бы одно равенство прямых полей или одношаговых разыменований присоединяемого и любого более раннего источника, дополнительно — скалярные фильтры через `И`; при разыменовании в `ПО` соединения разыменования выводятся группой рядом со своим источником; ссылка на источник, присоединяемый позже, — диагностика; путь глубже одного шага в `ПО` — диагностика; `ПОЛНОЕ` компилируется в нативный `FULL JOIN` и ведёт себя как остальные соединения: допустимо в цепочке, под агрегатами и с группировкой, разыменование в его `ПО` выносится внутрь своей стороны; платформа вместо `FULL JOIN` шлёт разложение — `UNION ALL` внутреннего соединения и двух антисоединений через `НЕ СУЩЕСТВУЕТ` (замерено на 8.3.27), но на равенстве оба отвечают одинаково, что сверено пробами построчно; условие `ПО` остаётся цепочкой равенств через `И`, иначе сервер откажется планировать соединение |
| ✅ | `ГДЕ` / `WHERE` |  |
| ✅ | `СГРУППИРОВАТЬ ПО` / `GROUP BY`, `ИМЕЮЩИЕ` / `HAVING` | ключи — путь поля (одно разыменование), псевдоним проекции или выражение, совпадающее с проекцией; проекция, которая не читает ни одного поля источника, — константа набора строк: её не требуется ни группировать, ни ставить рядом с агрегатом (как отвечает платформа); каждая неагрегатная проекция обязана быть ключом; ссылочный ключ группируется по всем физическим членам; `ИМЕЮЩИЕ` — предикат с агрегатами; сортировка сгруппированной ветви — только по ключам и псевдонимам; с `ПОЛНОЕ СОЕДИНЕНИЕ` группировка разрешена и отвечает как платформа |
| ❌ | `СГРУППИРОВАТЬ [ВСЕ] ПО ГРУППИРУЮЩИМ НАБОРАМ ((…),(…))` / `GROUP BY GROUPING SETS` |  |
| ✅ | `ОБЪЕДИНИТЬ [ВСЕ]` / `UNION [ALL]` | ветви должны совпадать по числу значений; значения разных типов образуют составное значение, как на платформе — замерено на 8.3.27: каждая ветвь пишет член своего типа, ноль остальных членов и тег своего типа, и все члены остаются `NULL`, пока значение ветви `NULL`; ветвь, которая уже выдаёт члены, сохраняет свой порядок, остальные подстраиваются под неё; ссылки разной ширины по-прежнему приводятся к `RTRef ‖ RRRef`; колонки, не являющиеся членами одного значения, — диагностика. Отличие: у объединения только скалярных ветвей порядок членов наш (значение первым, `_TYPE` последним, как у `ВЫБОР`), у платформы `_TYPE` первым — на результат это не влияет, обе стороны объединения согласованы между собой |
| 🟡 | `УПОРЯДОЧИТЬ ПО … ВОЗР/УБЫВ` / `ORDER BY … ASC/DESC` | только в конце запроса; ключ — поле, псевдоним проекции или любое выражение (`ВЫБОР`, арифметика, `ЕСТЬNULL`, `ТИПЗНАЧЕНИЯ`), порядковые номера не поддержаны; при `JOIN`, группировке и `ОБЪЕДИНИТЬ` порядок задаётся по колонкам результата, поэтому ключ обязан быть полем проекции или псевдонимом, а выражение отклоняется; с `ИТОГИ` ключ может отсутствовать в проекции — он выводится скрытой колонкой `__order_<n>`; упорядочивание по типу идёт в порядке кодировки (Неопределено, примитивы, ссылки по номеру таблицы), как на платформе |
| ❌ | `УПОРЯДОЧИТЬ ПО … [ВОЗР/УБЫВ] ИЕРАРХИЯ` / `HIERARCHY` |  |
| ❌ | `АВТОУПОРЯДОЧИВАНИЕ` / `AUTOORDER` |  |
| 🟡 | `ИТОГИ [поля] ПО [ОБЩИЕ] точки [[ТОЛЬКО] ИЕРАРХИЯ] [ПЕРИОДАМИ(…)]` / `TOTALS … BY [OVERALL] … [[ONLY] HIERARCHY] [PERIODS]` | результат — строки обхода `Прямой`: общий итог, затем итог каждой группы перед её строками, группы в порядке первого появления в упорядоченной выборке; итоговые поля — агрегаты по колонкам результата (агрегат пишется в свою колонку, выражение — в колонку из `КАК`), в прочих колонках `NULL`; контрольная точка — колонка результата (точка вне списка выборки — диагностика, платформа допускает); `ПЕРИОДАМИ` разбирается и проверяется, но строк не добавляет (платформа дополняет периоды только в обходе по группировкам); `CompileOptions::totals_level` добавляет колонку `__level` = `Уровень()`, консоль её включает; `ИЕРАРХИЯ`/`ТОЛЬКО ИЕРАРХИЯ` — одна контрольная точка (вторая — `UnsupportedFeature`) с одноцелевой ссылкой на иерархический справочник (иначе `Syntax`): строка итога по иерархии для каждой папки-предка через рекурсивные CTE по `_ParentIDRRef` (`WITH RECURSIVE` на PostgreSQL; на SQL Server действует `MAXRECURSION` 100), она суммирует строки самой папки и всех потомков; уровень папки — её глубина, итог группы на уровень ниже строки над ним (у папки-ключа — ниже её собственной строки иерархии), детальная запись ещё ниже, при `ОБЩИЕ` всё на единицу глубже; при `ТОЛЬКО` группировка по родителю значения; `ПО X, X ИЕРАРХИЯ` равносильно `ПО X ИЕРАРХИЯ`; родители ищутся по базовой таблице и таблицам расширений справочника; сверено с платформой на четырёх пробах построчно; отличие: папки-соседи идут в порядке первого появления строк под ними, тогда как платформа сортирует их по полям `УПОРЯДОЧИТЬ ПО`, вычисленным для самих папок; с `ПОМЕСТИТЬ` — `Syntax`, во вложенных запросах — `UnsupportedFeature` |
| ❌ | `ДЛЯ ИЗМЕНЕНИЯ [OF таблицы]` / `FOR UPDATE [OF]` | компилятор только для чтения |
| ✅ | `[НЕ] В (вложенный запрос)` | подзапрос с одной колонкой совместимого вида либо с колонками-членами одного составного значения: замерено на 8.3.27, платформа сравнивает члены рядом (`(TYPE, S, RTRef, RRRef) IN (SELECT …)`), раскладывая вторую сторону по тем же членам — свой член несёт значение, дискриминатор — тег, остальные — ноль своего типа, и все они остаются `NULL`, пока значение `NULL`; на SQL Server строкового сравнения нет, поэтому составная форма там отклоняется диагностикой; составное значение с внешней стороны отвечает своими членами, а если его членов не хватает — диагностика; строковый член сравнивается как текст с обеих сторон; колонки, не являющиеся членами одного значения, — диагностика, как раньше; источники внешнего оператора видны в подзапросе по своему псевдониму (коррелированный подзапрос), безымянное поле по-прежнему ищется только среди собственных источников, а производный источник `ИЗ (…)` внешние псевдонимы не видит — SQL вычисляет его до внешней строки; ссылки сравниваются на одной ширине (fixed сторона расширяется до `RTRef ‖ RRRef`); подзапросы в списке выбора — ❌ (их нет и в 1С) |
| 🟡 | Пакет запросов `;` | операторы пакета компилируются последовательно (не более 64) и собираются в один SQL-оператор: результат даёт последний, как `Запрос.Выполнить()`; промежуточные запросы без `ПОМЕСТИТЬ` только проверяются; массива результатов, как у `ВыполнитьПакет()`, нет; пакет из одного `УНИЧТОЖИТЬ` строк не возвращает |
| 🟡 | Разыменование `Поле.Реквизит[.Реквизит…]` | сколько угодно шагов: каждый шаг присоединяет цель предыдущего, одинаковые шаги ветви делят одно соединение; допустимо в проекции, `ГДЕ`, `СГРУППИРОВАТЬ ПО`, `УПОРЯДОЧИТЬ ПО`, а в `ПО` соединения — только один шаг, в том числе у `ПОЛНОЕ`; имя таблицы можно опускать, если поле уникально среди источников; продолжать путь через составную ссылку нельзя — диагностика, платформа так умеет |
| ✅ | Поле-пара `RTRef ‖ RRRef` (`Регистратор`, `Ссылка` журнала, payload критерия) как значение | такая пара — всегда ссылка, `_TYPE` у неё нет; замерено на 8.3.27 на регистре с двумя видами регистратора: платформа принимает её значением везде — в проекции, `ВЫБОР`, `ЕСТЬNULL`, сравнении (почленном), `ЕСТЬ NULL` (оба члена), `ССЫЛКА` (по `_RTRef`), группировке и упорядочивании (оба члена) и в агрегате (по склейке членов). Здесь пара в выражении рендерится своим payload `RTRef ‖ RRRef` с видом runtime-typed ссылки, `ТИПЗНАЧЕНИЯ` от неё — тег ссылки рядом с номером таблицы из `_RTRef`, агрегат берётся от payload |
| ✅ | Разыменование составного поля (`ЛюбаяСсылка`, `Регистратор`, payload подзапроса или ВТ) | цели берутся из SchemaStorage, из описания типа в Config, из вида колонки подзапроса либо перебором ссылочных объектов; SchemaStorage не называет цели ссылки, допускающей несколько таблиц (`["R",0,0,"",4]` против `["R",0,0,"Reference53",3]`), но их называет Config: у объекта третий идентификатор его класса — это ссылочный тип, которым его называют другие, а у реквизита есть описание `{"Pattern", {"#", <ссылочный тип>}, …}` (и то и другое замерено на 8.3.27 на пробной конфигурации); описание типа может называть целый вид, а не объект («любой справочник», «любой бизнес-процесс», «любая ссылка») — это десять платформенных констант, замеренных на 8.3.27, и такой тип раскрывается во все объекты своего вида; если же описание называет не хранимый объект (определяемый тип, характеристику), список остаётся пустым и работает перебор, и стандартные поля в нём распознаются по имени, так что `Т.Регистратор.Дата` и `Т.Объект.Родитель` разыменовываются; если присоединяемых целей больше 256 (столько таблиц принимает в одном операторе SQL Server), нужна ВЫРАЗИТЬ; предел считает цели, которые действительно дают соединение, а не кандидатов перебора: корпусный запрос перебирает больше 256 объектов и соединяет 94, давая 65 КБ SQL со 188 `LEFT JOIN`, который живой сервер планирует и выполняет; на каждую цель `LEFT JOIN` с охраной по типу, значение — `ВЫБОР` по `_RTRef`, для типов без реквизита `NULL`; цели, которые типизируют реквизит по-разному, дают одно составное значение: каждая пишет член своего типа, ноль остальных членов и тег своего типа, и все они остаются `NULL`, пока значение этой цели `NULL` (замерено на 8.3.27, форма та же, что у `ВЫБОР` разнотипных ветвей); ссылки расширяются до `RTRef ‖ RRRef`; путь продолжается за составной шаг — замерено на 8.3.27: остаток пути проходится внутри каждой цели (соединения после составного шага идут без охраны, потому что цель уже фиксирована), ветви выбираются тем же `CASE` по типу, а цель, в которой остаток пути не разрешается, в результат не попадает; составной шаг глубже вкладывает ещё один `CASE`; больше 256 целей и представление результата — диагностика |
| ✅ | `.Представление` / `.Presentation` | через callback-план приложения (см. README «Callback ABI представлений») |

## 2. Операторы

Грамматика логических выражений по страницам «Логические выражения в языке
запросов» и «Логические операторы»: сравнение `> < = >= <= <>`, `[НЕ] В [ИЕРАРХИИ]
(список | подзапрос)`, `[НЕ] МЕЖДУ … И …`, `ЕСТЬ [НЕ] NULL`, `ССЫЛКА <Имя
таблицы>`, `[НЕ] ПОДОБНО … [СПЕЦСИМВОЛ …]`, связки `И ИЛИ НЕ`.

| Статус | Оператор | Примечание / реакция |
| --- | --- | --- |
| ✅ | `+ - * /` | `%` — ❌ (в справке не описан) |
| ✅ | `+` как конкатенация строк | замерено на 8.3.27: платформа склеивает строки и отказывает, если рядом со строкой стоит другой тип («Неверные параметры "+"»), — здесь так же; операнды приводятся к тексту, вид выражения — `String` |
| ✅ | `= <> < > <= >=` |  |
| 🟡 | Сравнение составного поля со значением (`=`, `<>`, `В`) | предикат собирается по физическим членам, как это делает платформа: `_TYPE` сравнивается с тегом типа значения, а член этого типа — со значением; ссылка сравнивает ещё и `_RTRef`, а поле с единственным ссылочным типом хранит `_RTRef` не отдельной колонкой, и он синтезируется из `_TYPE`; значение типа, который поле хранить не может, даёт пустую выборку, а параметр без значения — сравнение с `NULL`; сравнение двух составных полей, `>`/`<` (платформа упорядочивает по тегу типа) и `ЕСТЬNULL` над составным полем не поддержаны — диагностика |
| ✅ | Логическое выражение как значение | сравнение, `И`/`ИЛИ`/`НЕ`, `ЕСТЬ NULL`, `ПОДОБНО`, `МЕЖДУ`, `ССЫЛКА` и `В` отвечают булевым значением в проекции, ветви `ВЫБОР` и упорядочивании; `NULL` в операнде даёт `NULL` — замерено на 8.3.27. На PostgreSQL это само предикатное выражение, на SQL Server булевых значений нет, поэтому значение рендерится трёхветочным `CASE WHEN p THEN 0x01 WHEN NOT p THEN 0x00 END` (сохраняет `NULL`), а предикатная позиция остаётся обычным предикатом |
| ✅ | `И` / `ИЛИ` / `НЕ` (`AND` / `OR` / `NOT`) | приоритет замерен на платформе: `НЕ` слабее любого сравнения и сильнее `И`, поэтому `НЕ Т.Цена = 10` отрицает сравнение, а `НЕ А > 10 И Б < 30` отрицает только первое; `НЕ` покрывает также `ПОДОБНО`, `В`, `В ИЕРАРХИИ`, `ССЫЛКА` и `ЕСТЬ NULL`; унарные `+` и `-` по-прежнему относятся к своему операнду; отличие: `НЕ х МЕЖДУ а И б` платформа не принимает (нужно `х НЕ МЕЖДУ а И б`), мы разбираем как отрицание сравнения; на MSSQL булевы поля в предикатах приводятся к `= 0x01` |
| ✅ | `В (список)` / `IN (...)` | непустой список скалярных выражений, в том числе `ЗНАЧЕНИЕ(...)` |
| ✅ | `НЕ В (список)` / `NOT IN` |  |
| ✅ | `[НЕ] В ИЕРАРХИИ (…)` / `IN HIERARCHY` | значение совпадает с элементом списка или лежит под ним по цепочке `_ParentIDRRef`; спуск — рекурсивная CTE на каждый предикат (`WITH RECURSIVE` на PostgreSQL, `WITH` на SQL Server), проверка через `EXISTS`, поэтому `NULL` в списке ничего не портит; пустая ссылка охватывает весь справочник, а справочник без колонки родителя вырождается в обычное вхождение — как на платформе; слева — поле с единственной ссылочной целью либо составная ссылка: у составной сравнивается идентификатор, а тип обязан совпасть с типом семян, потому что значение другого типа ни под каким семенем не лежит (замерено на 8.3.27); если тип семян неизвестен при компиляции — например, параметр связан `NULL` — спуск не строится и остаётся сравнение идентификаторов, которые уникальны; справа — вложенный запрос или константы (поле в списке — диагностика, CTE не видит внешнюю строку); в операторе с `ПОМЕСТИТЬ` — диагностика, так как тело временной таблицы само становится CTE |
| ✅ | `[НЕ] МЕЖДУ … И …` / `BETWEEN` | границы включаются, обратные границы дают пустую выборку, `NULL` не совпадает — как на платформе; значение и границы — любые скалярные выражения |
| ✅ | `[НЕ] ПОДОБНО … [СПЕЦСИМВОЛ …]` / `[NOT] LIKE … [ESCAPE …]` | шаблон передаётся в `LIKE` без переписывания на обоих провайдерах (на PostgreSQL классы `[…]` обеспечивает `mchar`); операнды — строки; принимается и как значение (проекция, `ВЫБОР`, упорядочивание), как на платформе |
| ✅ | `ЕСТЬ NULL` / `ЕСТЬ НЕ NULL` (`IS [NOT] NULL`) | составное поле и универсальная ссылка проверяются по одному члену — `_TYPE`, иначе `RRRef`: он `NULL` ровно тогда, когда строки нет, поэтому у собственных строк таблицы ответ всегда ЛОЖЬ, а у непопавшей строки внешнего соединения — ИСТИНА, как на платформе |
| ✅ | `ССЫЛКА Справочник.X` / `REFS` | операнд — прямое поле или одношаговое разыменование; составное поле сравнивает `_RTRef` с номером типа, payload вложенного запроса — первые четыре байта; поле с единственной целью даёт `ИСТИНА` и для пустой ссылки, как платформа; чужой тип и нессылочное поле — `Syntax` (в 1С «Несовместимые типы») |
| ✅ | `ВЫБОР [выражение] КОГДА … ТОГДА … [ИНАЧЕ …] КОНЕЦ` / `CASE [expr] WHEN … THEN … [ELSE …] END` | простая форма сравнивает каждую альтернативу с выражением после `ВЫБОР` по тем же правилам, что и сравнение в `ГДЕ` (ссылки, составные поля, значения типа); `NULL` в выражении не совпадает ни с одной альтернативой, как на платформе; ветки разных типов дают значение составного типа: в проекции оно раскладывается по членам (`<имя>` — payload ссылки, `<имя>_S`, `<имя>_N`, `<имя>_T`, `<имя>_L` и `<имя>_TYPE`), каждая ветка пишет своё значение в свой член и нули в остальные — так же хранит и возвращает платформа; ветка, состоящая из одних `NULL` (например вложенный `ВЫБОР` по несвязанным параметрам), получает тип альтернативы: без этого PostgreSQL читает её как `text` и отвергает соседство с payload ссылки; двоичные данные и `УникальныйИдентификатор` члена в раскладке 1С не имеют (такое значение не попадает в таблицу), поэтому получают собственные члены `<имя>_B` и `<имя>_U` с тегом `NULL` — платформа отвечает на такую ветвь двоичными данными, а `ТИПЗНАЧЕНИЯ` от неё даёт `Null` (замерено на 8.3.27); `ТИПЗНАЧЕНИЯ` от самого разнотипного `ВЫБОР` пока не компилируется; вне проекции разнотипные ветки — диагностика, кроме `ПРЕДСТАВЛЕНИЕ`: оно проталкивается в ветви и даёт одну строковую колонку (строковая ветвь — сама строка, ссылочная — представление по плану приложения), как отвечает платформа (замерено на 8.3.27); ветвь, представимая только отложенным протоколом, — диагностика; вид результата — первая не-`NULL` ветвь, остальные должны быть совместимы; ссылки на разные объекты расширяются до runtime-typed payload; агрегаты внутри `ВЫБОР` допустимы в сгруппированных ветвях и в ветвях из одних агрегатов |

| ❌ | `РАЗМЕРХРАНИМЫХДАННЫХ` | английское написание в справке не приведено |

| ✅ | `Ссылка` / `Ref` (`ID`), `Код` / `Code`, `Наименование` / `Description`, `ПометкаУдаления` / `DeletionMark` (`Marked`), `ВерсияДанных` / `Version`, `Номер` / `Number`, `Дата` / `Date`, `Проведен` / `Posted`, `Регистратор` / `Recorder`, `НомерСтроки` / `LineNumber` (`LineNo`), `Период` / `Period`, `Активность` / `Active`, `Родитель` / `Parent` (`ParentID`), `Владелец` / `Owner` (`OwnerID`) | у каждого из четырнадцати полей принимаются оба синонима — русский и схемный |
| 🟡 | `Предопределенный` / `Predefined`, `ЭтоГруппа` / `IsFolder` | вычисляются, как на платформе: `ЭтоГруппа` — отрицание колонки `Folder` (она хранит ИСТИНУ у элемента), `Предопределенный` — непустой `PredefinedID`; отвечают в проекции, `ГДЕ`, группировке, упорядочивании и через ссылку, вид колонки — `Boolean`; в `*` не попадают, там остаются схемные колонки |
| ✅ | Стандартные поля бизнес-процессов и задач: `Завершен`/`Completed`, `Стартован`/`Started`, `ВедущаяЗадача`/`HeadTask`, `Наименование`/`Name`, `Выполнена`/`Executed`, `БизнесПроцесс`/`BusinessProcess`, `ТочкаМаршрута`/`Point` | имена проверены на платформе на пробной конфигурации с бизнес-процессом и его задачей |
| 🟡 | `ИмяПредопределенныхДанных` / `PredefinedDataName` | сопоставляется с именем предопределённого элемента, объявленным в конфигурации: строка с именем, пустая строка у непредопределённой записи, `NULL` у непопавшей строки соединения; вид колонки — `String`. Платформа хранит идентификатор и переводит его в имя вне SQL, поэтому упорядочивание и сравнения `<`/`>` идут по имени, а не по идентификатору, `ПОДОБНО` и строковые функции над полем принимаются (платформа их запрещает), а имя, которого нет, даёт пустую выборку, а не ошибку |
| ✅ | `ВидДвижения` / `RecordType` | принимается и схемное имя из SchemaStorage (`RecordKind`); имя запроса проверено на платформе |
| 🟡 | `МоментВремени` / `PointInTime` | пара «дата + ссылка», физической колонки за ней нет: у документа это `Дата` и `Ссылка`, у записи регистра, подчинённого регистратору, — `Период` и `Регистратор`. Замерено на 8.3.27: платформа раскладывает пару на две колонки выборки (`<имя>_T` — дата, `<имя>` — ссылка), на два члена в `УПОРЯДОЧИТЬ ПО`, `СГРУППИРОВАТЬ ПО` и `РАЗЛИЧНЫЕ`; так же поступает и компилятор. У справочника и у независимого регистра сведений поля нет — диагностика, как на платформе; агрегат и разыменование платформа тоже запрещает. Отличие: сравнение двух моментов времени платформа раскрывает лексикографически (`дата >`, при равенстве — ссылка), здесь пара в выражениях отклоняется диагностикой |
| ✅ | `Источник.Представление` / `Presentation` | представление собственной ссылки источника; путь тот же, что у `ПРЕДСТАВЛЕНИЕССЫЛКИ(Источник.Ссылка)` — план представления запрашивается у приложения; источник без собственной ссылки — диагностика |
| ✅ | `ТипЗначения` / `ValueType` у плана видов характеристик | колонка `Type` объекта |
| ✅ | `Порядок` / `Order` у перечисления | колонка `EnumOrder`: порядок объявления значения, начиная с нуля (замерено на платформе) |
| ✅ | Реквизиты, добавленные расширениями | по `_ExtensionsRestruct` |

## 6. Литералы, параметры, комментарии

По странице «Константы и параметры в языке запросов» литералами являются
`ИСТИНА`, `ЛОЖЬ`, число, строка, `ДАТАВРЕМЯ(…)`, `ТИП(…)`, параметр `&Имя`,
`НЕОПРЕДЕЛЕНО`, `NULL`.

| Статус | Элемент | Примечание |
| --- | --- | --- |
| ✅ | Строки `"…"` с удвоением `""` | многострочные литералы с `\|` — ❌ |
| ✅ | Числа |  |
| ✅ | `ИСТИНА` / `ЛОЖЬ` / `NULL` (`TRUE` / `FALSE`) |  |
| 🟡 | `НЕОПРЕДЕЛЕНО` / `UNDEFINED` | компилируется в `NULL`, вид колонки — `Undefined`; сравнение с литералом сравнивает тип значения с типом «Неопределено»: составное поле совпадает только при теге `0x01`, значение вида, который не может хранить `Неопределено` (двоичное, `УникальныйИдентификатор`, тип), даёт константный предикат ЛОЖЬ (`<>` — ИСТИНА), как платформа возвращает пустую выборку вместо ошибки; в `ВЫБОР`, `ЕСТЬNULL` и `ОБЪЕДИНИТЬ` совместим с любым видом, как `NULL`; отличие от 1С: в результате `Неопределено` неотличимо от `NULL` |

| ✅ | Параметры `&Имя` | значения передаются через `CompileOptions::parameters` и инлайнятся типизированными литералами (`Null`, `Boolean`, `Number`, `String`, `Date`, `Reference`, `Binary`, `List` только в `В (…)`); в консоли — `\set`, `\params`, `\unset` |
| ✅ | Параметры сеанса `&Имя` | расширение open-sdbl: `CompileOptions::session` (`SessionParameters`) видны всем запросам и ограничениям доступа сеанса; параметр запроса с тем же именем имеет приоритет; неиспользованный параметр сеанса — не ошибка; в консоли — `\session` |
| ✅ | Разделители данных (общие реквизиты `Разделять`) | как в 1С: каждая разделённая таблица получает `_Fld<N> = <значение>`, значение — из параметра сеанса, привязанного к разделителю в `Config` (иначе по имени реквизита); без значения `Независимо и совместно` фильтруется пустым значением, `Независимо` — диагностика `Parameter`; параметр использования `ЛОЖЬ` отключает предикат |

## 7. Что open-sdbl добавляет сверх языка 1С

- Бинарные литералы `0x…`.
- Ключевое слово `ON` вместо `ПО` в условии соединения; короткие английские
  имена видов метаданных (`Reference`, `InfoRg`, `AccumRg`, …) и физические
  имена стандартных полей (`Folder`, `ParentID`, `RecordKind`, …).
- `ColumnKind` для каждой колонки результата и нативные типы вместо текста.
- Колонка `__level` у результата с `ИТОГИ` (по опции
  `CompileOptions::totals_level`, в консоли включена): уровень строки, как
  `Уровень()` у выборки по группировкам, потому что результат — плоский
  набор строк, а не дерево.
- Параметры сеанса: `SessionParameters` видны каждому запросу и каждому
  ограничению доступа, в отличие от параметров одного `Запрос`а.
- Разделители данных без значения в сеансе фильтруются пустым значением
  (общие данные), а не читаются целиком; платформа в этом случае не
  фильтрует.
- Прикладная политика вместо ролей конфигурации: представления значений
  (`PresentationPlan`) и построчные ограничения `РАЗРЕШЕННЫЕ`
  (`AccessRestriction`) приходят от приложения через callback, потому что
  ядро не выполняет ввод-вывод и не читает роли.
- Уровень диалекта MSSQL (`2008`/`2012`), поддержка PostgreSQL 9.0+ и баз
  платформы 8.2 без `PartNo`.
